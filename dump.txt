1. SPACE DESK — MVP DESCRIPTION
-------------------------------

spacedesk, in MVP terms, can be described as:

"spacedesk is software that lets you use another device—such as a laptop, tablet, or phone—as an additional display for your main computer over a network."

The simplest MVP requires:

1. Host app — runs on the main PC and captures/provides its display output.
2. Client app — runs on the secondary device and displays the received frames.
3. Network connection — transfers display data between the two devices.
4. Virtual display — the host creates an additional monitor that the operating system can use.
5. Basic input forwarding — optionally sends touch/mouse input from the client back to the host.

In one sentence:

"spacedesk MVP = turn a second device into a wireless/network-connected secondary monitor for your PC."

Everything beyond that—multiple displays, touch support, resolution/orientation controls, performance optimization, USB/network options, etc.—is additional functionality built around that core concept.

2. SPACE DESK AND USB ANDROID COMMUNICATION
-------------------------------------------

The discussion distinguished spacedesk's native Android USB mode from ordinary USB tethering.

Important distinction:

- Native spacedesk Android USB mode is a dedicated USB connection mechanism.
- spacedesk documentation discusses Android Open Accessory Protocol (AOAP) in relation to Android USB compatibility.
- USB tethering is different: Android exposes a network interface over USB, and ordinary TCP/IP networking can then run through it.
- Native spacedesk USB mode should not be simplistically described as "USB networking + TCP/IP."

Conceptual native USB architecture:

Windows PC
    |
    | spacedesk host / display pipeline
    |
    | USB / AOAP-related transport
    |
Android spacedesk Viewer
    |
    | rendering

Conceptual USB tethering architecture:

Windows
    |
    | USB
    |
Android USB network interface
    |
    | TCP/IP
    |
spacedesk Viewer

AOAP should be understood as the USB accessory/access mechanism, not automatically as the entire proprietary spacedesk display protocol.

The exact proprietary spacedesk application-level protocol is not publicly documented in the material discussed.

4. THE VIRTUAL DISPLAY IS THE KEY
---------------------------------

The central concept is that Windows is made to believe it has another monitor.

Conceptually:

GPU
    |
    +-- Monitor 1 -> physical laptop display
    |
    +-- Monitor 2 -> spacedesk virtual display

Windows display settings can therefore expose a second display.

For example:

Display 1:
    1920x1080 physical laptop panel

Display 2:
    1920x1080 spacedesk virtual display

When a user moves a window onto Display 2, Windows itself renders that window into the virtual display's surface/framebuffer.

This is why spacedesk can act as a desktop extension rather than merely mirroring an existing screen.

The host's display driver effectively tells Windows:

"I am another display device. Here are my supported resolutions, orientations, modes, etc."

6. WHY RAW FRAMES ARE IMPRACTICAL
---------------------------------

Example:

1920 x 1080 x 4 bytes per pixel
= 8,294,400 bytes
= about 7.9 MiB per raw frame

At 60 FPS:

8.29 MB x 60
~ 498 MB/s

This is far too much for ordinary network display streaming.

Therefore compression/video encoding is required.

12. ANDROID SESSION ESTABLISHMENT
---------------------------------

When the Android Viewer starts:

1. Initialize networking/display components.
2. Discover available hosts.
3. User selects a host.
4. Viewer establishes a display session.
5. Host and client negotiate configuration/capabilities.
6. Windows configures a virtual display.
7. Host starts streaming it.
8. Android receives and renders the stream.

Negotiated information may include:

- display dimensions
- orientation
- supported encoding/compression
- input capabilities
- display configuration
- transport/session parameters

Exact proprietary negotiation packets are not publicly documented.

20. LINUX SUPPORT IN SPACE DESK
-------------------------------

At the time of discussion, official spacedesk host/primary-machine support is Windows-focused.

Therefore the project opportunity is:

Build an open-source spacedesk-like host specifically for Linux.

21. ORD PROJECT CONCEPT
-----------------------

Project name:

ORD

Expanded name:

OpenRemoteDisplay

Goal:

Build an open-source Linux-native alternative to the user-facing concept of spacedesk.

Core behavior:

Linux computer exposes a real virtual display.
Android device connects to it.
Android becomes a secondary monitor.
Linux desktop treats it as an additional display.

Do NOT simply build VNC/screen sharing.

Do NOT clone the proprietary spacedesk protocol.

Use an original open protocol and implementation.

24. ORD VIRTUAL DISPLAY
-----------------------

This is the hardest and most important host component.

Potential approaches discussed:

A. DRM/KMS virtual display

Create a virtual DRM connector/output.

Conceptual Linux display layout:

DRM/KMS
    |
    +-- HDMI-1
    +-- DP-1
    +-- ORD-1

B. Compositor-specific virtual output

Possible backends for:

- GNOME/Mutter
- KDE/KWin
- COSMIC
- wlroots

This can be easier in some cases but increases maintenance.

C. EVDI

EVDI provides virtual display functionality and is used by some Linux display/streaming projects.

Could be a useful MVP/backend option if appropriate.

The project should not blindly choose one approach. Inspect the actual system and current Linux APIs.

60. FAILURE HANDLING
--------------------

Host unavailable:
    Android shows Host unavailable.

Decoder unavailable:
    Android explains that a compatible H.264 decoder is unavailable.

Encoder unavailable:
    Host falls back to software.

Virtual display unavailable:
    Host reports useful diagnostics.

Network disconnect:
    cleanly terminate and reconnect if enabled.

Display configuration failure:
    do not leave GNOME in a broken state.

61. CLEAN SHUTDOWN
------------------

When Android disconnects:

1. Stop video stream.
2. Release session.
3. Destroy/disable virtual display.
4. Restore normal display state if needed.
5. Release encoder.
6. Release capture resources.
7. Release network resources.

Avoid ghost displays.
